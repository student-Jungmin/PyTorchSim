# Tests that pass THROUGH the Triton codegen route.
# Gated by scripts/ci/triton_route_sweep.py; regenerate with
#   python scripts/ci/triton_route_sweep.py --all --update-allowlist
# A test that passes without emitting a kernel is deliberately absent.
# WHAT WAS BLOCKED HERE AND IS NOT. tests/models/test_swinv2.py stopped after
# 26 kernels because transformers' Swinv2Layer.get_attn_mask builds its
# shifted-window mask with `torch.zeros(...)` and no `device=`, so an
# input-independent constant stayed on the host INSIDE the traced graph and
# Inductor emitted a C++ kernel for it -- which its own CPU vectorizer then
# failed to compile (`decltype` of a scalar float, then
# `Vectorized<float>::blendv`), reproducible with stock torch and PyTorchSim not
# imported at all.
#
# Two ways out were measured. `cpp.simdlen = 0` makes the C++ compile, and was
# declined: it is process-wide and it hides someone else's defect. Naming the
# default device for the compiled call removes the island instead -- the mask is
# built on the device and this backend compiles it like any other elementwise
# work. 26 kernels and a compile error before; 27 kernels, no C++ kernel at all,
# and 4.77e-06 after. The test carries the two-line scope and the reasoning.
#
# WHAT SD1.5 NEEDED, since it is the newest and the longest entry here.
# tests/models/Diffusion/test_diffusion.py runs the UNet2DConditionModel at
# reduced channel counts: 87 kernels compiled, 220 executed, and it stopped
# three times before it ran.
#   buf3    GroupNorm's Welford mean, 32 of 32 channels equal to the mean over
#           the whole tile -- the gather's rank-1 index vector pinned the loop
#           body to the reduction axis while the accumulators kept the other
#           one, because lib_axis_graph had no scf.for edge (triton-npu).
#   kernel 83  a segfault on the SECOND trip round a reduction loop: a gather
#           index non-affine in the loop variable had the loop offset added to
#           the base as well as carried in the index tensor (triton_shared,
#           PtrAnalysis::rebuildAsGatherScatter).
#   buf20   eight reports against add_N nodes nothing materialises -- the
#           per-kernel verify checked buffers a kernel only READS, and
#           Inductor can name an in_out_ptr the kernel never stores to.
# Runtime here is about 11 minutes, inside the sweep's 1800s default.
#
# WHY test_llama3x.py IS HERE WHEN test_llama3.py ALREADY IS. It gates a width,
# not an architecture. test_llama3.py runs 1024 hidden, which puts head_dim at
# 32 -- a quarter of the array -- and no shipped Llama is that shape, so it says
# nothing about how the real block tiles. test_llama3x's default is one layer of
# the real 8B block (4096 hidden, head_dim 128, SwiGLU 14336) plus the vocab
# projection: 285M parameters, 23 kernels, 8.58e-06, 301s. It also carries the
# 3.2 shapes -- 3B's n_rep=3 is the first non-power-of-two GQA repeat in the
# suite -- and 3.1's rope scaling, which is guarded because that scaling folds
# into inv_freq at construction and a test can otherwise "pass 3.1" while
# compiling Llama 3's graph unchanged. Nothing here was broken when it was
# written; the entry is a floor, not a fix.
#
# test_mllama.py IS THE ONE THAT NEEDED A BACKEND FIX. Llama 3.2 Vision's
# cross-attention decoder layer stopped in triton-npu's absorb_layout with
# "indexing map cannot take the move": a single-input elementwise generic whose
# move drops a unit middle axis, leaving no operand naming that dim, so linalg
# could not infer the loop's bound -- which for a unit dim is 1. Fixed in
# triton-npu 2988424, and the pin in thirdparty/triton-npu.json moves with it.
# Both towers run: vision 4.2915e-06, text 3.4019e-06, 8m07s for the pair.
# The vision width is NOT the real 1280 on purpose -- test_vit.py and
# test_clip.py already gate ViT-shaped attention at 768, and what was unproven
# was the tile structure and the local/global split, which scaling keeps.
#
# WHY tests/models/Qwen/test_qwen.py RUNS TWO PRESETS WHERE EVERY OTHER ENTRY
# RUNS ONE. It gates a family, not a model: Qwen2/2.5 carry a QKV bias that no
# other block in this suite has, Qwen3 drops it and adds an RMSNorm per head
# over head_dim (q_norm/k_norm), and the two MoE lines differ from each other by
# a gated shared expert. No single preset is the whole claim, so the default
# runs `3-8b` (Qwen3 at its real 4096 width, 260M params, 19 kernels, 6.68e-06)
# and `2-moe` (the QKV bias plus routed + shared-expert MoE, 36 kernels,
# 2.42e-06) -- 519s for the no-argument run, on a machine that was running four
# other model tests at the time. n_rep=7 at the real 7B width, Qwen3-MoE and the decoupled
# head_dim are one `--preset` each and are not in the gate.
#
# AND WHAT IT COST TO GET THERE, since the entry would otherwise look free:
# Qwen3's q_norm fuses with rope into a persistent reduction, 27 live
# scratchpad tiles, 1625120 bytes/lane against a 131072 budget. The retry in
# triton_backend/codecache.py halved R0_BLOCK, which a persistent reduction
# bakes into its own body -- so 128, 8 and 1 all measured the SAME overflow and
# the kernel was refused. It now shrinks only a block the kernel takes as an
# argument, XBLOCK when a reduction takes none.
#
# WHY tests/models/Yolo/test_yolo.py GATES TWO OF NINE VERSIONS. It covers the
# ultralytics model parser, one preset per version directory under
# ultralytics/cfg/models -- v3, v5, v6, v8, v9, v10, 11, 12, 26 -- built from
# YAML with random weights, no checkpoint and no torch.hub. The existing
# tests/models/Yolov5/test_yolov5.py keeps the hub path and the pretrained
# weights; this file is the config-built counterpart across generations, and
# the parser fits its modern anchor-free head onto every version, so a preset
# here is a claim about the BACKBONE and NECK.
#
# v5 (C3 + SPPF) and v8 (C2f) pass at 1.85e-05 and 1.15e-05 relative and are
# the gate: 1128s for the no-argument run, measured the way the sweep runs it.
# The other seven do not pass, and none of them is merely "not tried" -- each
# has a measured stop, written out in the test's docstring:
#   v6            stops in the DEVICE. Its ConvTranspose2d neck is not lowered
#                 by Inductor, so it goes out as extern_kernels.convolution and
#                 dispatches to convolution_overrideable, which
#                 PyTorchSimDevice/csrc does not register. Same gap as
#                 RecurrentGemma's conv1d, and v6 shows it is not 1-D specific.
#   v3, v9        WERE wrong and now PASS (2.93e-06 and 1.15e-04), on a
#                 triton_shared this repo does not yet pin. Both were one bug:
#                 PtrState::rebuildAsGatherScatter zeroed the constant offset
#                 that distinguishes a pool window's four loads, so the four
#                 became one, CSE merged them and canonicalize folded the max
#                 away -- v3 returned silu of the top-left element, v9's
#                 avg_pool returned (a+a+a+a)/4. Fixed in PSAL-POSTECH/
#                 triton_shared b6c3e60 (1304 of 1311 dumped kernels
#                 byte-identical after it; all 7 that changed are pools).
#                 THEY ARE NOT GATED because setup/versions.env still pins
#                 TRITON_SHARED_SHA 9017bd4e, which needs a prebuilt release to
#                 move; on the pinned binary they still fail.
#   v10 11 12 26  SEGFAULTED on the old pin -- the PSA depthwise conv faults on
#                 its SECOND grid iteration. Fixed by triton-npu a616ea5, which
#                 removed a p11 repair measured as never firing and which this
#                 kernel drives True twice. The pin now carries it, so all four
#                 RUN and are merely wrong.
#
# THE PIN MOVED WITH THIS, and it is a MERGE rather than a bump. 2988424 (the
# p09 unit-axis fix test_mllama.py is gated on) is NOT an ancestor of triton-npu
# develop -- it carries five commits that never landed there -- so pinning
# develop alone would have taken a616ea5 and dropped the p09 fix, and mllama
# would have started failing for a reason nothing in this file mentions.
# thirdparty/triton-npu.json now points at 98744f7, develop merged with that
# line -- one commit carrying p09 (mllama), p11 (the YOLO segfault) and p13
# (7aec83d, Qwen2-VL's replicate axes, which landed on develop while this pin
# was being moved). Re-measured on it: resnet, mllama (both towers, 4.2915e-06
# / 3.4019e-06) and this gate (1.85e-05 / 1.15e-05) all pass, and the four YOLO
# versions above return max rels identical to their a616ea5 runs to every
# digit.
